Kraki 抗网络波动：测试方案

分支 test/network-resilience（基于 main 985a310）。目标：iOS/Mac ↔ Head、Tentacle ↔ Head 在各种网络波动下达到可测量的生产级标准。完整版见仓库 docs/network-resilience-test-plan.md。

1. “生产级”的量化目标

#指标目标
G1消息不丢显示为已发送/发送中的输入，网络恢复后 100% 送达
G2消息不重agent 收到每个 clientId 恰好一次
G3不误报失败断网 ≤60 秒、带宽占满、延迟尖峰：0 次“失败”，无需手动重试
G4恢复快重连 p95 ≤3 秒；积压发送回显、漏掉的新消息补齐 p95 ≤5 秒
G5死链检测半开连接 ≤30 秒发现
G6不误杀链路在传数据时 0 次被判死；一次真实断网只重连 1 次
G7顺序完整恢复后按 seq 连续，无空洞、乱序、重复气泡
G8状态诚实“重连中”只在断开 ≥2 秒显示；气泡状态与事实一致
G9资源有界断网 2 小时，内存/磁盘/重连频率有上限
G10进程重启App 被杀、Head/Tentacle 重启后，未确认输入仍恰好一次送达

发布门槛：协议级全部场景 + 1000 次随机混沌 0 违例；原生核心场景全过；8 小时浸泡 0 违例。

2. 代码里已看到的缺口（先写测试证实，再修）

① 没有自动重试。发出后 20 秒没回显就变“未确认”，只能手动点重试。生产里见过 13–52 秒的回显延迟，带宽一满必然触发——这很可能就是你看到的高失败率。
② Mac 发送被拒时静默无反应。刚启动/刚重连时 agent 公钥还没就绪，发送直接被拒，输入框什么都不做（iOS 会弹失败）。应排队而不是拒绝。
③ 输入在 Head 上不持久。agent 离线超过 5 分钟被清理，Head 重启直接丢。
④ App 侧发送队列只在内存。进程被杀后恢复成“未确认”，但不会自动重发。
⑤ 心跳在拥塞时误判。链路被大数据占满时 pong 排不上，被当死链踢掉（本次断线风暴的直接原因）。
⑥ Tentacle 重连固定 3 秒，无退避无抖动。Head 重启时惊群；长断网时空转。
⑦ “重连中”没有去抖。瞬断也会闪。

5. 分层与顺序

层内容何时跑
T0重试/退避/心跳判定单元测试（假时钟）每次 CI
T1本地 Head + 真实 Tentacle + mock app + chaos-proxy，场景 A–FPR 精简集；1000 次夜间
T2原生无头驱动 + 模拟器/Kraki Dev UI 状态客户端 PR / 夜间
T3netem 丢包乱序、NLC 预设、8 小时浸泡、事故剖面回放发布前
T4线上诊断看板：重连次数、回显延迟、未确认比例持续

顺序：①搭环境（代理、一键本地栈、对账器）→ ②在未改动的 main 上跑出基线红灯与数字 → ③按缺口逐个修，优先级：自动重试与分级超时、发送排队、心跳不误杀、Head 持久化输入、Tentacle 退避抖动、状态去抖、App 队列持久化，每项以场景由红转绿为证 → ④精简集进 PR 门禁（按改动范围触发），混沌与浸泡手动/夜间，不进每次门禁。

本分支只放测试设施与方案；每个产品修复单独提 PR，附红转绿证据。
